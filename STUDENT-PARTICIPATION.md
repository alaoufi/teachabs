# Single-student participation and lesson resources

This release supports one authenticated teacher seat and one student seat derived from the booking's parent account. It does not implement a multi-student roster or separate student identities.

The workspace selector has three views: teacher board, student draft, and approved student contribution. Only the teacher edits the teacher board. Only the student edits the draft, and only while the teacher grants permission. The teacher can inspect the draft, publish a snapshot or hide the published snapshot. Further edits to the draft do not silently change the approved copy. Hiding removes the approved copy, retaining the draft. Approval is visible in the dedicated approved-contribution view, not merged destructively into the teacher's drawings.

All changes use server revisions. Stale concurrent writes are rejected and retained locally for export/manual recovery. Changing lessons archives each lesson's teacher board, draft and approved contribution, and revokes student writing until granted again. Archived lessons are omitted from client responses. Current lesson resources are selected on the server against authenticated booking subject and grade. Preview lesson assignments are explicitly synthetic, not official curriculum mappings. Freehand drawing remains freeform; this is not semantic classification of what a user writes.

Teacher departure offers export, keeping the work, explicit clearing or cancellation. Only a confirmed teacher request may clear the current lesson's teacher board, draft and approved contribution; other lessons and account/booking records are untouched. The teacher's authorized clear endpoint can operate after the booking time ends. Browser/tab closure cannot reliably display a custom dialog and does not automatically clear anything. Unsent/conflicting work blocks the destructive button. JSON export preserves the current lesson snapshot; the existing generic import UI restores its top-level teacher scene, not an entire multi-view archive automatically.

Validation: server permission and stale-revision tests; HTTP rejection of wrong subject, parent clearing and unrelated teacher clearing; two-browser-seat draft, publication, hiding, reconnect, reload, cancellation and confirmed-clear scenarios. These tests use synthetic local data. No live deployment was performed for these changes. No external provider or new licensed asset was added.

Multi-student support requires per-student authenticated membership and draft storage keys, seat-filtered server serialization and events, individual grants/revocation, a teacher review queue, presence records and cross-student confidentiality tests. The current two-seat implementation must not be advertised as supporting those capabilities.
